Project Overview & System Requirements

SparkEV is a personalized, predictive and explainable EV intelligence system. Four prediction modules turn real-world EV data into driver-specific guidance; SHAP explains every prediction, FedPer federated learning keeps raw vehicle data private, and the tree models run on-device on an ESP32. Results flow from the ESP32 over Wi-Fi to a FastAPI server, which generates recommendations for a React dashboard.

Server, Tools & Dashboard

  • • Python 3.11 or later (tested with 3.13)
  • • FastAPI + Uvicorn backend (backend/server.py)
  • • Node.js 20+ for the React (Vite) dashboard
  • • requirements.txt for server & tools
  • • requirements-notebooks.txt for research notebooks

Firmware & Hardware

  • • ESP32 dev board @ 240 MHz, ~520 KB RAM
  • • SH1106 OLED display (128×64, I2C @ 0x3C)
  • • Arduino IDE 2.x with ESP32 board support
  • • Libraries: Adafruit GFX, Adafruit SH110X
  • • Total on-device inference: 8.65 ms
+---------------------------+  Wi-Fi (JSON)  +-----------------------+  every second  +-------------------+
|  ESP32 with OLED display  | -------------> |  FastAPI server       | <------------- |  React dashboard  |
|  Module 1: stress         |                |  backend/server.py    |                |  dashboard/       |
|  Module 2: charging       |                |  - validates results  |                |  - scores         |
|  Module 3: battery health |                |  - generates advice   |                |  - risk levels    |

How the pieces work together Notebooks train the models → models/ holds the trained files → esp32/tools/ converts them into C headers → the ESP32 firmware runs all three models on-device and POSTs the results to backend/server.py → the server generates recommendations → the React dashboard polls GET /latest every second and displays scores, risk levels and advice.

Setup & Installation Instructions

Step 1: Clone Repository 
git clone https://github.com/saravanapriyaa21/sparkEV.git
cd sparkEV

All runnable code lives in the sparkEV repository. This website is a visual guide to it — every command below runs from inside the cloned sparkEV/ folder.

Step 2: Add the Datasets

Datasets are not included (size and licences). Place these files in data/raw/ — the server checks for them on startup and stops with an error if one is missing:

FilesUsed by
LFP01_fast_feature.xlsx, NMC02_fast_feature.xlsx, Lab_fast_feature.xlsx, NMC01_Car01_fast_feature.xlsx, NMC01_slow_feature.xlsx, NMC01_Car02_fast_feature.xlsxModule 3
processed_data_longer_than_30.xlsxModule 2
Step 3: Configure Python Environment 
# Linux / macOS:
python3 -m venv venv
source venv/bin/activate

# Windows:
python -m venv venv
venv\Scripts\activate

pip install -r requirements.txt
# Optional, for the research notebooks:
pip install -r requirements-notebooks.txt
Step 4: Start the Server 
uvicorn server:app --app-dir backend --host 0.0.0.0 --port 8000

--host 0.0.0.0 makes the server reachable from the ESP32 on the same network. Interactive API docs: http://localhost:8000/docs.

Step 5: Start the Dashboard (second terminal) 
cd dashboard
npm install
npm run dev
# Open http://localhost:5173

API Endpoints & Request / Response Schemas

Base URL when running locally: http://localhost:8000

MethodEndpointUsed byPurpose
GET/AnyoneHealth check
POST/esp32/resultESP32Send results of the three on-device models
GET/latestDashboardMost recent result with recommendations (polled every second)
POST/predictDevelopersRun the models on the computer, for testing without hardware
POST /esp32/result

Called by the ESP32 after running all three models. The server runs no model here — it validates the driver, generates recommendations and stores the result. Errors: 400 unknown driver_id, 422 missing / wrongly typed field.

Before any result arrives it returns a waiting status. Afterwards it returns all request fields plus recommendations, prediction_id and server_latency_ms; battery_risk is normalised to Low / Medium / High.

Model Artifacts, Inputs & Results

Module / Artifact Algorithm Inputs → Output Result
M1 · model1_battery_stress_xgb.json XGBoost, 300 trees 24 features → BSI (0–100) R² = 0.831 (trip-grouped CV), 0.805 unseen trips
M2 · model2_charging_fault_xgb.pkl XGBoost, 300 trees 57 features → P(faulty) 99.62% Acc, F1 = 0.981 (52/54 faults, 0 false alarms)
M3 · model3_battery_degradation_xgb.pkl XGBoost, 3×100 trees · Direct AR 199 features → SOH, capacity, corrected capacity R² = 0.959 (SOH 10 cycles ahead)
M4 · energy & arrival SOC Elastic Net Trip features → kWh, arrival SOC R² = 0.897 energy; 0.932–0.984 arrival SOC
Federated learning (Modules 1 & 4) FedAvg and FedPer were compared with centralized training. For arrival SOC, federated learning nearly matches centralized training (R² 0.973 vs 0.976). For battery stress, FedPer achieves lower error than FedAvg for 32 of 51 clients.

Instructions for Running Each Part

1. Test the pipeline without the ESP32: 
curl -X POST http://localhost:8000/predict \
     -H "Content-Type: application/json" \
     -d '{"driver_id": 17}'

Runs all three models on the computer; the result also appears on the dashboard.

2. Reproduce the research notebooks (Modules 1–4, FL): 
jupyter notebook notebooks/

Set the data location near the top of each notebook (e.g. data_path or MODULE_DIR), then run top to bottom. Notebooks also run in Google Colab with data in Google Drive.

3. Convert retrained models to C headers: 
python esp32/tools/convert_model1_to_esp32.py
python esp32/tools/convert_model2_to_esp32.py
python esp32/tools/convert_model3_to_esp32.py
python esp32/tools/verify_model3_converter.py   # checks C-rule traversal matches XGBoost
4. Regenerate input vectors for drivers 17 & 24: 
python esp32/tools/export_model2_driver17.py
python esp32/tools/export_model2_driver24.py
python esp32/tools/export_model3_driver17.py
python esp32/tools/export_model3_driver24.py
python esp32/tools/convert_model2_driver_vectors.py
python esp32/tools/convert_model3_driver_vectors.py

Each exporter saves a reference prediction in esp32/tools/vectors/ — compare it with the OLED output to confirm parity.

09

ESP32 Edge Microcontroller Deployment

XGBoost cannot run on a 520 KB device, but a trained model is just decision trees. Each tree is exported into const C arrays (stored in flash) and evaluated with a short loop — no ML library needed. Missing values (NAN) and categorical splits follow XGBoost's rules. Module 2 applies a sigmoid to produce a probability.

ESP32 to SH1106 OLED Pinout

  • • OLED VCC → ESP32 3.3V
  • • OLED GND → ESP32 GND
  • • OLED SDA → ESP32 GPIO 21
  • • OLED SCL → ESP32 GPIO 22
  • • I2C address: 0x3C

Upload Steps (Arduino IDE)

  1. Install Adafruit GFX + Adafruit SH110X
  2. Open SparkEV_Integrated.ino
  3. Board: ESP32 Dev Module + port
  4. Partition: Huge APP (3MB No OTA/1MB SPIFFS)
  5. Upload; Serial Monitor @ 115200 baud
ModelSample outputPrediction time
Module 1: battery stressStress 62.39, MODERATE3.35 ms
Module 2: charging anomalyP(fault) 1.000, Faulty1.92 ms
Module 3: battery healthSOH 91.76%, risk LOW3.38 ms
Total (sequential)8.65 ms

Firmware uses ~2.0 MB flash (63% of Huge APP) and 50 KB RAM (15%). Over 20 transmissions the server averaged 17.5 ms processing; network round trip over a mobile hotspot was 52–589 ms (median 188 ms) — the network, not the model, is the bottleneck.

Troubleshooting & Known Limitations

Server stops with "Model 3 dataset not found"

A dataset file is missing from data/raw/. See Setup Step 2.

Dashboard shows "Waiting for ESP32 data"

No result has reached the server yet. Check the ESP32 is running, or send the /predict test request.

ESP32 cannot reach the server

SERVER_URL must use your computer's local IP (not localhost), both devices must share a network, and the server must run with --host 0.0.0.0.

Upload fails: "text section exceeds available space in board"

Set Tools > Partition Scheme to Huge APP (3MB No OTA/1MB SPIFFS).

Display stays blank

Check the wiring and that the display uses I2C address 0x3C.

Current limitations (addressed in Roadmap Phase 6)
  • The ESP32 uses prepared input vectors for two demo drivers; feature preparation runs on the computer.
  • Module 4 (linear model) is not yet part of the on-device test.
  • Only inference runs on-device; on-device training of the FedPer personal layer is untested.
